1. 建议与目标

把当前能用的本机健康档案，逐步发展成“随手记录、原件可查、历史连贯、就医时拿得出来”的个人与家庭健康应用。

建议采用 React + TypeScript + Vite 共用主要界面，Capacitor 承载手机端，Tauri 承载桌面端，Python 逐步迁入 FastAPI，初期保留 SQLite 的路线。现有 OCR、检验解析、图表、AI 和 MCP 能力分模块保留，不进行一次性重写。需要正式多账号服务或较高并发时，再迁移 PostgreSQL。

建设顺序：可靠保存与恢复 → 数据来源统一 → Web 核心流程 → 安全的跨设备访问 → 手机和桌面安装包 → 离线编辑及设备集成。

1.1 目标用户与使用方式

  • 本人管理自己的就诊、报告、用药及日常健康记录。
  • 获得授权的家庭管理者管理多位成员，录入和查看时始终知道当前是谁。
  • 手机主要用于拍照、随手记录、临时查阅；电脑主要用于集中整理、对照趋势、备份及导出。
  • 首轮采用个人或家庭私有部署，不默认把现有档案上传第三方云端。

1.2 首轮成功标准

  • 一段文字或一份原件就能形成有效记录；普通就诊速记以 60 秒内完成为设计目标，需实际测试验证。
  • 保存成功必须能在刷新后读回；失败保留输入，不能只显示成功提示。
  • 就诊、报告、用药及后续事项可在同一详情流程中关联查看。
  • 各端在连接同一服务时看到同一成员的已提交数据，成员切换不串档。
  • 可在全新目录恢复全部成员、原件及关联关系，并核对一致性。

1.3 首轮范围外

不建设医院业务系统、在线诊疗、自动处方、医疗影像诊断、多租户商业平台或设备持续后台采集。DICOM 原件优先保存和下载，专业阅片另行评估。公开分享、家庭邀请和逐条记录授权不作为首轮前提。

2. 当前项目的真实起点

本节依据现有代码和技术文档检查，不读取或复述个人健康记录，不把历史任务清单当作当前完成状态。本轮未运行功能回归，以下“已有”表示存在实现，仍需后续验收。

方面 当前可见实现 后续重点
前端 HTML/CSS/JavaScript；index.html 按顺序加载 js/app.*.js，已有独立视图和 ECharts 封装 消除共享全局状态，建立类型及组件边界
服务端 Python health_server.py 提供本机 HTTP、数据库 API、原件访问及 OCR；默认监听回环地址，支持环境配置 逐步分层，远程使用前增加完整认证与授权
结构化数据 SQLite，包含检验、报告、就诊、用药、病史、体征、症状、饮食、睡眠及待办等 统一来源、逐条写入、版本控制及迁移管理
原件与旧档案 原件文件、私有 Markdown/HTML、assets/data.js 摘要与数据库并存 建立记录级来源映射，减少重复手写与路径依赖
报告导入 文本、图片 OCR、CSV、JSON 备份及预览确认流程 多页报告、日期确认、定性结果和重复检测验收
家庭成员 members 名单，默认成员与新增成员分别使用数据库和图片目录 当前是本机切换，不是独立账号权限体系
AI / MCP 按成员检索的 AI 问答、历史记录、来源展示及本机 MCP 读写 权限收敛、引用定位、写入审计及恢复
备份与导出 SQLite 快照、按成员 JSON 导出及原件相关实现 统一覆盖全部成员、附件和 AI 历史，并做恢复演练
验证工具 解析、服务、OCR、原件导入、功能集成及文档链接检查脚本 隔离测试库，扩展到跨端与权限场景

2.1 优先处理的问题

  1. 写入确认不足。 js/app.core.js 的 pushJSON 发起异步请求，但没有把完成结果返回给调用方；迁移时必须让业务流程等待持久化结果，或明确进入可恢复的待提交队列。
  2. 整表替换不适合多设备。 部分现有 PUT 接口以数组替换整类记录，两台设备基于旧快照保存可能相互覆盖；增加版本检查和逐条命令后再开放多设备写入。
  3. 事实仍有多个载体。 Markdown、静态摘要和数据库职责尚需收敛；先建立可核对映射，再迁移，不能直接删除旧文件。
  4. 本机信任边界不能直接用于远程。 当前已有 Origin 检查、agent 凭证与静态白名单，但常规页面 API 不是完整登录授权系统，部分私有 HTML 和原件仍可通过静态路径访问。公网或家庭多账号使用前必须统一授权所有数据通道。
  5. 多成员恢复范围不完整。 现有说明指出 JSON 导出不包含 AI 历史，定时滚动备份任务仍只覆盖默认成员；应以恢复清单核实每位成员和每类文件。

历史 HANDOFF、架构诊断与重构方案 保留参考价值，但其中“单文件前端”“没有静态白名单”等描述不能继续作为当前事实。任务状态应重新验收，不直接沿用“待办”或“已完成”的旧结论。

3. 产品结构与核心场景

沿用 个人健康档案体验重设计 中已明确的方向，一级入口保持稳定。

入口 主要内容 优先动作
首页 当前成员、快捷记录、到期待办、最近记录 记就诊、存报告、记日常
就医记录 就诊、报告、用药的综合时间线与搜索 找记录、看原件、导出摘要
日常健康 体重、体征、症状、睡眠、饮食等记录和趋势 快速记录、查看变化
健康主题 用户主动关注的问题或目标及相关资料 关联记录、整理阶段小结
我的 个人资料、重要病史、成员、备份、连接和模型设置 管理档案与数据

AI 问答从首页或相关详情进入；首次使用与空档案不强制配置模型。成员切换保留在全局可见位置。

3.1 记一次就诊

打开速记 → 确认成员和日期 → 输入一段文字或添加原件 → 保存 → 在最近记录中看到结果。医院、科室、医生、诊断和医嘱可渐进补充；后续关联用药及提醒，不连续强迫填写。

3.2 存一份报告

拍照或选文件 → 核对成员 → 保存多页原件 → 可选 OCR → 核对识别结果 → 确认写入。识别失败仍可保存原件；缺日期保留“未确认”，不能用上传时间冒充检查日期。

3.3 准备一次复诊

选时间范围或健康主题 → 查看相关就诊、报告和用药 → 补充要问医生的问题 → 预览摘要 → 导出。重要信息缺失显示“未记录”；导出范围可选，并保留指向原记录的来源标识。

3.4 记录日常变化

直接打开最近使用的记录类型，默认当前日期但允许修改；测量条件、单位与设备来源可记录。缺数据不补零；不同项目、样本和不兼容单位不强行画成同一趋势。

3.5 管理家庭档案

切换成员前处理未保存内容；录入、搜索、AI、导出和附件均跟随当前成员。未来账号授权与成员身份分开：一个账号可被授予多个档案的访问权，档案本人也未必持有登录账号。

4. 记录模型与事实来源

术语统一见 项目术语表。下表是目标模型，不要求首轮把所有现有表改名。

对象 主要内容 关系及边界
档案成员 Profile 称呼、关系、可选基础资料 每条健康记录明确所属成员
登录账号 Account / Grant 登录身份、档案访问授权 与成员分开；后端检查权限
就诊 Encounter 事件日期、自由记录、可选机构与医嘱 可关联多份报告、用药和待办
报告 Report 名称、日期状态、机构、原始文本 可独立存在，包含多页附件和结果
附件 Attachment 文件类型、大小、校验值、来源及归属 以文件 ID 访问，不把目录路径作为业务身份
检验结果 Lab Result 项目、原始值、数值/定性值、比较符号、单位、样本及参考范围 原始结果与规范化结果分别保留，可关联报告
用药 Medication Record 药名、原文用法、状态、起止及来源 历史记录不会自动成为当前在用药
日常记录 体征、体重、症状、睡眠、饮食等 保持各类记录语义，不塞进一个无约束文本表
健康主题 Health Topic 标题、关注状态、整理小结 与相关记录多对多；科室作为分类，不决定存储目录
随访待办 Follow-up Task 内容、类型、可选日期、状态及来源 用户确认后建立；无日期不判逾期
来源与分析 来源类型、原记录及版本、生成时间、人工确认状态 本人描述、医生原文、设备数据和辅助分析分开

4.1 通用数据规则

  • 新记录使用跨设备唯一 ID，保留旧 ID 与旧路径映射。记录具有 profile_id、revision、创建/更新时间、来源；支持离线同步后增加删除标记及变更日志。
  • 事件日期与录入时间分开；日期精度可为日、月或未知。测量时间保存时区信息，历史无时区记录不自行推断。
  • 更新不以客户端时间决定覆盖顺序；服务端比较版本，检测冲突。修改来源文件不悄悄改写已经确认的结构化结果。
  • 检验的 <、>、阴性、阳性和原始文本需要保留。缺参考范围不能判为正常；超参考范围只是报告信息，不等同于诊断。
  • 不用“同一天＋同项目”作为永久身份：同一天可能多次检测。重复判断结合报告、样本、测量时间、来源及原件校验值，疑似重复由人确认。
  • 一个报告可有多页，但同日多份报告不自动合并。一个健康主题可跨科室，一次就诊也可关联多个主题。

4.2 单一事实来源

内容 维护位置 其他载体的角色
可编辑健康记录 经确认的结构化数据库 页面、时间线和趋势只作查询视图
来源原件 附件存储及其索引 OCR 和缩略图是派生结果，不替代原件
自由叙述与整理小结 有成员归属、来源和版本的记录正文 Markdown 可保留为迁移来源或导出格式
AI 回答 独立分析记录及引用快照 不覆盖原始病历，不自动升级为确诊
技术说明 docs/ 不包含个人指标、诊断、机构、药名或具体就诊信息

“单一来源”允许设备缓存和备份存在，含义是同一事实只有一条明确维护链。迁移完成后不再人工同步修改数据库、data.js 和 Markdown 三处。

5. 技术栈与复用边界

前一轮的通用建议偏向全 TypeScript；本项目已积累 Python OCR、数据库和 AI 代码，因此后端继续 Python 更合适。数据库也按部署需要演进，不为跨端目标立即更换。

层 建议 与当前项目的衔接
主要前端 React + TypeScript + Vite 按功能迁移，旧页面继续可用；表单、模型、API 客户端集中维护
图表 保留 ECharts 复用图表配置与指标规则，补键盘和移动端交互
Web 响应式 SPA，后续补 PWA 首轮不需要 SSR；应用数据由 API 提供
手机 Capacitor 复用界面；相机、文件、权限、通知使用平台适配层
桌面 Tauri 2 复用界面；处理文件导出、窗口与凭证存储
服务端 Python + FastAPI，逐步替换标准库路由 提取服务层，复用 OCR、AI 及数据访问逻辑；OpenAPI 生成前端类型
数据库 初期 SQLite；有正式多人并发及运维需求后评估 PostgreSQL 先加迁移版本、事务和一致性约束，禁止客户端直接连库
原件 初期服务端私有目录与授权下载；后续可接对象存储 文件 ID 解耦物理路径；下载与缩略图执行相同权限检查
工程 pnpm workspace 管理前端；Python 独立依赖锁定 共用界面、类型和适配契约，不要求所有代码同语言
验证 保留现有脚本；关键 API 回归及 Playwright 核心流程 仅使用临时目录、合成数据和模拟模型

Capacitor 的官方定位是以 Web 界面和原生容器构建移动应用；Tauri 允许使用 HTML/CSS/JavaScript 前端，并提供原生集成。两者满足本项目以录入、检索和图表为主的初步方向，但平台插件仍需实机验证。Capacitor 文档、Tauri 文档

FastAPI 提供基于 Python 类型声明的接口校验及 API 文档能力，适合把当前脚本服务逐步整理为明确接口。FastAPI 文档

5.1 跨端复用的实际边界

  • 共享：业务模型、校验、日期和单位规则、搜索筛选、图表配置、大部分组件与 API 类型。
  • 分别适配：拍照、文件选择、凭证存储、分享、通知、网络状态、应用生命周期及安全区域。
  • 分别设计：手机卡片与底部导航、桌面双栏和批量整理；不把电脑宽表格缩小后直接当手机版。
  • 现有 Python OCR 不会随 Web 前端自动在手机运行。初期联网调用服务端 OCR，断网仍能保存待上传原件；离线 OCR 作为独立能力评估。
  • 新桌面版首轮连接同一私有服务，不自动在每台电脑复制一套独立 Python 服务。现有单机启动方式继续作为迁移期入口。
  • 若后续核心转向蓝牙持续采集、HealthKit/Health Connect 或后台任务，先验证插件和系统限制；验证不通过再评估 React Native/Expo，不承诺 Web 容器覆盖所有需求。
  • iOS/macOS 的构建、签名和分发需要相应 Apple 环境；Windows 开发机不能单独完成所有平台本地构建。

6. 部署、跨设备与离线策略

6.1 首轮默认：私有服务统一数据

保留当前本机模式；跨设备版本由用户选择的私有主机提供服务，Web、手机和桌面通过认证 API 使用同一份档案。远程访问采用受控 HTTPS 入口；是否部署在家用主机、私有服务器或其他环境，实施时单独确定。规划不等于授权部署或上传现有数据。

首轮以“联网提交成功即进入统一档案”为标准。跨端打包与数据同步是两项工作：有手机安装包不代表已经可以安全访问电脑上的数据库。

阶段 断网行为 联网行为
首轮 可选择缓存部分已读资料；表单保存为明确标识的本机草稿；附件保留在本机可靠存储后才提示已存草稿 提交成功才显示“已保存到档案”；失败不清空输入
后续 支持持久化的离线新增、修改队列，并显示待同步数量及失败原因 逐条幂等提交，处理版本冲突，拉取服务端变更

浏览器缓存可能被系统回收或被用户清除，不能作为唯一档案或可靠备份；无可靠附件持久化条件时必须明确提示，不显示保存成功。退出账号或撤销权限后处理敏感缓存。

6.2 开放多设备写入前的接口要求

  • 健康记录逐条创建、更新和删除；保留兼容旧接口的过渡层。
  • 修改带 expected_revision；版本不一致返回冲突，不覆盖另一设备的新内容。
  • 新增请求带幂等键，重试不会产生重复记录；保存与审计记录在事务中完成。
  • 客户端必须等待服务端提交结果，或者先可靠进入待提交队列；不依赖页面关闭时最后一次请求。
  • 初期可用刷新或轮询获取新数据，并展示最后刷新时间；持续在线推送按需要增加。

6.3 后续完整离线同步

原生端可评估 SQLite，Web 评估 IndexedDB；通过统一存储契约隔离平台。同步采用服务端游标和变更日志，支持删除标记、版本比较、失败重试及中断恢复。普通追加记录可合并；同一就诊正文或用药状态的并发修改保留双方版本，交由用户确认。

附件与记录分开传输，校验完整后再标记可用。清楚显示“本机草稿／待上传／已同步／有冲突”，并区分记录已同步与原件未上传。完整离线写入不作为首轮隐含承诺。

7. 数据保护、备份与恢复

7.1 从本机到远程的必要改造

  • 后端从认证身份计算可访问成员；请求中的 profile_id 只用于选择目标，不能作为授权证明。
  • 授权覆盖列表、搜索、原件、缩略图、静态私有档案、导出、AI 及 MCP。迁移后取消私有 HTML 和原件的直接静态访问，改为受控读取。
  • Web 使用安全会话机制；原生端使用系统安全存储。AI 密钥及其他服务端密钥不下发前端。
  • 记录访问和修改的必要审计信息，但日志不默认打印健康正文、原件内容、AI 提示词或密钥。
  • MCP 默认只读，写入按客户端、操作及成员范围授权；支持凭证撤销与轮换。当前全家庭 agent 凭证仅作为迁移期能力。
  • 网络传输与服务端存储分别设置保护措施；服务端可读取数据供 OCR/AI 使用的架构，不能宣称端到端加密。

7.2 完整备份范围

覆盖成员清单、每位成员数据库或统一库、报告及其他附件、自由记录、来源映射、主题关联、AI 历史、必要配置和备份清单。可撤销的访问凭证不作为健康档案导出内容；恢复后重新配置凭证。

数据库快照使用 SQLite Backup API 等一致性方式，避免在运行中的 WAL 数据库上只复制单个 .db 文件。SQLite 备份文档

完整备份还需协调数据库快照与附件：使用不可变文件、备份期间暂停清理或固定引用清单，校验快照引用的每个文件均存在，再发布备份完成标记。

建议初始策略：每日备份、迁移前强制备份，保留最近 30 日；每周另存一份到独立磁盘或用户选定位置。至少每月做一次隔离目录恢复演练。首轮目标为最多丢失 24 小时数据、普通规模档案 1 小时内恢复，实际需按原件体量实测。

备份失败需要可见提示；同盘快照只能防部分误操作，不能覆盖磁盘损坏。多端同步和给医生的摘要均不等于完整备份。

8. AI 与导入辅助

优先支持报告整理、跨记录检索、就医摘要和复诊问题准备。保留现有按成员检索与来源展示，逐步改为能定位到具体记录版本和原件页码。

  • 默认不配置远程模型；用户主动选择服务及数据范围后才发送相关内容。
  • OCR 与 AI 输出先进入待核对结果；确认后才写入正式记录。原图、提取原文、用户修订和模型分析分别保存。
  • AI 问答显示所依据的成员、时间范围、来源及截取限制；没检索到不能表述为没有病史。
  • 回答是辅助分析，不自动改写诊断、用药或复查安排；批量写入先提供变更预览。
  • 检索正文和附件文字属于不可信输入，不得据此改变授权、调用其他成员记录或执行删除命令。
  • 初期使用关系查询、文本搜索与现有检索规则；只有召回评估暴露明确问题时再引入向量检索。
  • AI 不可用时，录入、原件保存、搜索、备份及摘要导出仍可独立使用。

9. 历史数据迁移方案

每一步都可在临时副本上重跑，产出迁移日志与差异清单。未确认内容不能因换系统变成事实。

  1. 盘点与冻结基线。 检查现有未提交改动，列出代码、每位成员数据库、原件与私有文档范围；生成一致性备份及文件校验清单。代码版本与健康数据备份分开保存。
  2. 建立映射。 为旧记录 ID、成员、Markdown 路径、静态摘要及原件建立迁移映射；不先搬目录。
  3. 提取候选记录。 现有结构化数据直接迁移；Markdown 中的信息作为带来源的候选项，不能从目录名推断诊断、从影像日期虚构就诊。
  4. 处理重复与关联。 高置信度同源副本合并，疑似重复列入人工核对；保留原日期、单位、参考范围、原始文字及来源。
  5. 按成员对账。 比较各类记录数量、关键字段、附件校验值、关联完整性和未知项状态，生成可审阅报告。
  6. 试用与切换。 新版先对迁移副本验证；旧版保留只读查询，正式切换时短暂停写并迁移最后差异，避免两套同时独立写入。
  7. 关闭双重维护。 页面摘要和时间线从统一记录派生；旧文件只读归档或按需导出，不再三处手写。
  8. 回滚演练。 恢复切换前备份；新版试用期间新增内容先导出保全，不能回滚时直接丢弃。正式切换后的回滚需明确追加记录如何处理。

10. 迭代路线与验收门槛

按一名熟悉项目的开发者连续投入估算，首个可用跨端版本约 8–12 周；每阶段结束根据实际验证修正。商店审核、设备集成、完整离线同步和大量历史人工核对不计入首轮工期。

阶段 参考投入 主要交付 进入下一阶段的门槛
P0：可靠性基线 1–2 周 当前功能验收、等待写入结果、全部成员完整备份、版本检查原型、数据盘点 保存失败不报成功；隔离恢复可用；两端旧快照不会静默覆盖
P1：Web 核心闭环 2–3 周 新前端骨架、统一 API 类型、就诊/报告/日常/检索/摘要流程，服务层逐步抽离 五项核心任务完成；编辑不丢字段；同一记录只维护一次
P2：安全跨设备 2–3 周 单管理员登录、可访问档案校验、授权附件、私有部署方案、多设备版本冲突处理 未授权请求拿不到任何成员数据；跨端创建和修改可互相读回
P3：安装包与交付 2–3 周 Capacitor 手机包、Tauri 桌面包、签名构建流程、升级验证、使用说明 真机拍照和文件流程可用；升级不丢数据；备份恢复跨版本可用
P4：增强能力 单独估算 完整离线同步、家庭邀请授权、健康平台集成、智能检索优化 每项有独立验证方案，通过后逐步开放

实施时 P1 与 P2 的部分工作可以交错，但安全和并发写入验收必须早于跨设备正式使用。新功能发布前保留旧版可查询入口，避免迁移期中断日常记录。

12. 规划假设与需要后续确定的事项

本规划按“家庭规模、记录和检索为主、允许先联网后增强离线、不默认使用第三方云端”制定。以下事项在进入相关阶段时确定，不阻碍先做 P0：

  • 首发手机平台及可用真机；iOS/macOS 构建环境和分发渠道。
  • 私有服务运行位置、可用性要求，以及是否需要离开家庭网络访问。
  • 首轮是否仅一位管理员；家庭成员自行登录和授权邀请放在哪一阶段。
  • 是否需要断网独立编辑正式档案；若首轮就必须支持，应提前 P4 同步设计并重新估工。
  • 是否把系统健康平台、蓝牙设备或后台采集设为核心需求；需在选择手机容器前做能力验证。
  • 原件规模、影像保存方式及独立备份位置；据此调整存储和恢复目标。
