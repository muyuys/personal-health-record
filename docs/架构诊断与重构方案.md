# 健康档案 · 架构诊断与重构方案

> 只读分析产出，未改动任何代码或档案文件。分析对象：`server/health_server.py`、`assets/data.js`、`js/*`、`data/health.db`、`private_data/`、`Tools/*`。
> 目标：① 诊断"服务与数据"耦合；② 提出 `private_data/` 去重方案；③ 给出按科室的"病例(case)"目录结构方案与落地步骤。

## 第一部分 · 服务与数据耦合诊断

结论先行：本项目存在**三重数据轨**——同一份检验/就诊信息同时被写在 **①SQLite DB**、**②手写 `assets/data.js`**、**③`private_data/健康档案/*.md`** 三处，且后端、前端、生成脚本又各自**硬编码了中文主题名/目录结构/指标名**。这是数据腐化、结论过期、迁移困难的总根源。以下逐点列出（文件:行号）。

### 1.1 后端硬编码（server/health_server.py）

| 位置 | 硬编码内容 | 风险 |
| --- | --- | --- |

### 1.4 DB 与磁盘的"双轨/错位"

- **service 认知的原件目录 ≠ 真实原件目录**：后端只服务 `data/报告原件/files/`（`IMG_DIR`），但 `data/` 下真实影像原件分布在 `data/右脚踝/检查/…`（含完整 DICOM 序列，数十个子目录）、`data/照片/`；`reports` 表 5 条 `file` 字段指向 `/files/<uuid>.jpg`。**两套图片位置并存**，DB 记录的原件路径与磁盘真实文件不保证一一对应。
- **DB 有 45 条 labs / 5 条 reports / 2 条 weights / 1 条 body**，但 md 与 data.js 又各自把同样的数字抄了一遍（见 1.5）。
- **visit / medication / allergy / vitals / symptom 等表全部 0 行**，但 `就诊记录待填清单.md` 已按时间线列出 7 条候选就诊、`用药记录.md` 有内容——**信息只存在于 md，未入库**；而 `todo` 表只有 1 行，`复诊与待办.md` 却有多条。

### 1.5 三重轨重复的实证（同一事实写三处）

以"2026-09-04 肝肾功能 肌酐112/尿酸440/eGFR77.7"为例，同时存在于：
1. **DB**：`labs` 表 45 条中的肾功能 8 项 + 肝功能 12 项；
2. **`data.js`**：`issues` 里 liver 的 card/head/evidence（部分手写）；
3. **`健康档案/健康问题总表.md:12`（手写主题行）+ `:21-28`（AUTO 自动派生块）**。

以"右踝四次影像"为例，同一批骨折/韧带摘要同时存在于：
- `健康档案/检查与就诊时间线.md:7-15`；
- `健康档案/就诊记录待填清单.md:13-18`；
- `主题/右脚踝/longitudinal_analysis/右踝四次检查对照分析.md`；
- `data.js` 的 `timeline[]` 与 `issues[ankle].timeline`。

> 注意 `健康问题总表.md` 已有局部治理：`:16-29` 的 `<!-- AUTO:LABS -->` 块由 `生成问题总表.cjs` 从 DB 自动派生（方向正确），但**上方 `:5-14` 表格的"肝肾功能"行仍是手写**，两处并存，AUTO 块只覆盖"检验摘要"、没覆盖"主题结论"，所以双轨未真正消除。

### 1.6 耦合点清单小结与风险分级

**必须改（P0，直接影响数据正确性/安全）**
- 结论三处手写（`data.js` + 总表手写行 + md）→ 用户看到过期/错误结论；
- 后端宽静态托管整个 ROOT（PHI 泄露 + ACL 冲突根源）；
- `visit`/`medication` 已有 md 内容却未入库（信息孤岛）。

**应尽快改（P1）**
- `data.js` 硬编码中文主题路径（重组即死链）；
- 9 个 issue 只有 1 个走派生；
- 后端 `报告原件` 中文目录 vs 真实影像目录错位。

**可规划改（P2）**
- `CATS/PRESETS/SYMPTOM_PARTS/PRIORITY` 等前端常量；
- 生成脚本主题清单；
- 备份与主库同盘。

## 第二部分 · private_data/ 去重方案

### 2.1 重复类型盘点

**(A) md 与 html 孪生（机械重复，保留 md 为源）**
- 全部 26 个 md 都有同名 `.html`（`build-docs.cjs` 生成物，共约 60 文件中 html 占近一半）。**这些不是"内容重复"，是构建产物**。处置：html 一律视为派生物，`.gitignore` 或统一由 `build-docs.cjs` 重新生成，**不手工编辑、不作为去重对象**。

**(B) 同主题"多份 md"重复（真正的冗余）**
- `主题/眼睛/`：`2026-10-22_干眼与视觉症状沟通记录.md`（9689B，完整症状梳理）+ `病历.md`（119B，仅 3 行 2026-05-23 三种滴眼液）——**同一眼病拆成两文件**，应合并为一份"眼科病例"下的两条记录（症状沟通 + 用药小记），而非两个顶层主题文件。
- `主题/鼻子/`：`鼻炎.md`（空壳模板 0/5）+ `鼻中隔偏曲.md`（有 4 行真实内容）——**同科两文件**，应合并为"耳鼻喉科"下同一病例或两个并列 case。
- `主题/右脚踝/`：`ct_analysis/右踝CT辅助分析.md` + `longitudinal_analysis/右踝四次检查对照分析.md` + `右踝复诊沟通单.md`——三份并非重复（CT 读片 / 纵向对照 / 复诊沟通，各司其职），但**同属"骨科·右踝"一个病例**，应归到同一 case 目录，避免与健康档案时间线重复摘录影像结论。

**(C) 空壳模板重复（同构空文件）**
- `牙齿.md / 甲沟炎.md / 脚气.md / 鼻炎.md / 雄脱.md / 肝肾功能检查.md / 尿频尿急尿不尽.md` 全为同一五段模板、完整度 0/5（见 `Tools/生成主题档案.cjs` 模板）。**7 个结构完全相同的空壳**，本质是"待补占位"，不应各自成"主题"，而应由统一"病例模板"承载，按科室归位后标"待采集"。

**(D) 健康档案 ↔ 主题 交叉重复（最关键）**
- **化验/就诊记录双写**：`健康档案/检查与就诊时间线.md` 与 `就诊记录待填清单.md` 与 `data.js timeline[]` 与各主题影像分析，反复抄同一批右踝/眼科/鼻科/化验事件（见 1.5）。
- **化验结论双写**：`健康档案/健康问题总表.md` 手写行 vs AUTO 派生块 vs `data.js` vs `labs` 表。
- **减重**：`减重记录/目标与计划.md`、`每日记录/2026-10.md`、`weights` 表、`data.js.weight` 又各一份。

**(E) 旧版/新版并存**
- 未见明显 `_old`/`v2` 文件；但 `data/右脚踝/检查/` 下 2025-12/2026-02/2026-07/2026-08 四个检查各一目录是**时间序列**（非版本），应保留。
- `迁移修正链接.py` 暗示曾从"根目录按主题"迁到"docs+data 两根"，历史路径痕迹已清，但**md 内相对链接深度不一**（`../../data/…`、`../../../..`、`../../../../`），是迁移残留的脆弱点。

### 2.2 去重原则（单一事实源 SSOT）

| 信息类型 | 唯一事实源（SSOT） | 其它载体角色 |
| --- | --- | --- |
| 检验数值/异常 | **DB `labs`** | md/前端只读派生，不手写数值 |
| 影像报告结论 | **DB `reports` + 原件文件** | md 只写"解读/对照"，不重复抄报告全文三遍 |
| 就诊事件 | **DB `visit`**（当前 0 行，应先补录） | 时间线/待填清单降级为"视图"或干脆取消 |
| 症状主观描述 | 对应 case 的 md 正文 | 单一文件，不再拆两处 |
| 体重/围度 | **DB `weights`/`body`** | 减重.md 只写规则与复盘 |
| 档案结构/模板 | case 模板文件 | 空壳由模板+科室归位承载 |

### 2.3 去重执行清单（不改文件的建议动作，供后续执行）

1. **固化 html 为派生物**：`private_data/**/*.html` 纳入 `.gitignore`（或保留但声明不可手改），只维护 md；由 `build-docs.cjs` 统一重生成。
2. **合并眼科两文件**：`2026-10-22_干眼与视觉症状沟通记录.md` + `病历.md` → 一个 `眼科/干眼症/` case 下的"症状记录.md"与"用药-2026-05-23.md"（或合为一文件两节）。
3. **合并鼻科两文件**：`鼻炎.md`（空壳）+ `鼻中隔偏曲.md` → 归入 `耳鼻喉科/` 下各自 case；鼻炎 case 保留"待采集"标记。
4. **消除三轨结论**：`健康问题总表.md` 的**手写主题行全部改为 AUTO 派生**（扩展 `生成问题总表.cjs` 覆盖"主题结论"段，不止"检验摘要"）；`data.js` 的 issues 只保留"元信息+指向 case 的链接"，数值/结论由 `/api/all` 或派生函数注入。
5. **取消"时间线"手抄**：`检查与就诊时间线.md`、`就诊记录待填清单.md` 改为**从 `visit`+`reports`+`labs` 生成的视图**；先把 7 条候选就诊真正录入 `visit` 表（`docs/tasks/010/012`）。
6. **空壳模板统一**：7 个空壳不再各自等于"一个主题"，合并进统一的 case 模板 + 科室目录，标"待采集"；完整度由脚本计算。
7. **链接规范化**：迁移到新目录后统一用构建脚本重写相对链接（复用 `迁移修正链接.py` 思路，但改为**从配置生成**而非手写映射）。

```
    └── taxonomy.yaml                    # 科室↔case↔中文名↔源路径 映射配置（供脚本读取）
```

**关键设计点**
- **科室层（英文 slug）+ case 层**：与 `app.core.js`、`data.js`、生成脚本解耦——它们**只读 `taxonomy.yaml`**，不再硬编码中文主题名。
- **原件（影像 DICOM / 报告 jpg / 照片）仍留在 `data/`**（体积大、二进制），case 目录只放 **md 解读与链接**；后端 `ORIG_DIR` 改为"按 `taxonomy.yaml` 挂多个原件根"或统一迁到一个 `data/attachments/<case-id>/`，消除"报告原件 vs 右脚踝/照片"错位。
- **`problem` 多病症同科**：鼻中隔偏曲与鼻炎若视为同一患者同科两问题，可 `ent/<patient-nose>/case.md` 内分 `problems: [rhinitis, septum-deviation]`；简单起见先各成一 case。

### 3.4 风险与注意（执行前必看）
- **GUID/文件行号引用会失效**：现有 md 里 `../../data/右脚踝/…`、`../主题/肾功能/…` 等硬链接迁移后全断，必须用脚本统一重写并跑 `检查文档链接.py`。
- **同名合并需人工确认**：眼科两份、鼻科两份合并前，先确认时间/内容无冲突（本分析显示时间不同：05-23 用药 vs 10-22 症状，互补不冲突，可安全合并）。
- **空壳不是"删"而是"实例化"**：7 个空壳保留为 case 模板实例（标待采集），不要直接删——否则丢失"这些病存在但待补"的信息。
- **ACL 冲突根因**：宽托管整个 ROOT + 迁移时手移文件。**用脚本（服务态或脚本态）而非人工资源管理器搬迁**，且迁移前停服务。
- **一次只迁一层**：先 `data/` 原件不动，只迁 `private_data/*.md` 结构；二进制原件目录后置，避免大范围权限触碰。

---

## 一句话总结

系统骨架完整，但**同一事实写在 DB / data.js / md 三处，且三处都硬编码了中文主题名**——这是"结论过期 + 迁移困难 + ACL 冲突"的共同病根。正确的破法是：**先建 `taxonomy.yaml` 与患者级 `visit` 入库把单一事实源立起来，再用脚本按"科室/case"目录搬迁并让代码读配置而非写死名字**，而不是逐个手工改名。
