# 技术栈升级方案（前端 React+TS+Vite · 后端 FastAPI · 存储保持本地 SQLite）

版本：v1.0 · 日期：2026-11-09（香港时间）

性质：基于对现有代码的实读核对，给出可执行的升级/迁移方案。配套已落地的脚手架见 §8。数据存储层本轮**保持本地 SQLite 不变**，不做跨设备/多并发改造。

关联文档：[个人健康档案产品与技术规划](个人健康档案产品与技术规划.md)、[架构诊断与重构方案](架构诊断与重构方案.md)、[产品缺口分析](产品缺口分析.md)。

## 1. 本次升级的目标与非目标

### 1.1 目标
- 前端从「经典脚本 + 全局变量」升级为 **React + TypeScript + Vite**，按功能灰度迁移，旧页面继续可用。
- 后端从 `http.server` 升级为 **FastAPI**，抽服务层，复用现有 OCR / AI / 数据访问逻辑。
- 保持数据存储为**本地 SQLite**，但补齐 `revision`、迁移版本表与逐条写接口。

### 1.2 非目标（本轮明确不做）
- 不迁移 PostgreSQL；不做跨设备多账号写入；不做完整离线同步。
- 不一次性重写全部页面：只先迁移一条完整闭环（记就诊 → 查详情 → 编辑）作为样板。
- 不改动 `data/health.db` 现有数据与私有 `private_data/`。

## 2. 现状核对（基于实读代码，非文档转述）

| 项目 | 位置 | 现状事实 |
|---|---|---|
| 前端入口 | `index.html` | 按序 `<script>` 加载 13 个 `js/app.*.js`，共享全局作用域 |
| 全局状态 | `js/app.core.js:73-136` | `let labs / let state / let reports / let todoItems / let storeMode` 等 |
| 写入确认缺失 | `js/app.core.js:855` | `pushJSON()` 发起 `fetch().then().catch()`，**不返回 Promise**；所有 `saveXxx()` 均为 `pushJSON(...); return true;`（`app.core.js:984-1064`）→ 业务层无法 await 持久化结果 |
| 后端路由 | `server/health_server.py:1074-1143` | `do_PUT` 11 个 **整表替换** 接口：`/api/labs /api/reports /api/state /api/history /api/vitals /api/symptoms /api/diet-days /api/diet-weeks /api/sleep-logs /api/issue-status /api/todos` |
| 读取接口 | `server/health_server.py:1013-1073` | `GET /api/all`（一次性全量）、`/api/export`、`/api/originals`、`/files/*` |
| 路由包装 | `server/health_features.py:553` | `install(server)` 用 monkey-patch 包裹 `do_GET/do_PUT/do_POST` 注入 OCR/AI/MCP 路由 |
| 就诊持久化 | `server/health_server.py:534` | `replace_history()` 对 `visit` 表 `DELETE FROM visit` 后整批 `INSERT OR REPLACE` |
| 存储 | `data/health.db` | SQLite + WAL；`init_db()` 已含 `ALTER TABLE ... ADD COLUMN` 幂等迁移雏形 |
| 复用资产 | `assets/vendor/echarts.min.js`、`assets/markdown.js`、`assets/parse.js` | **本地 vendor、无第三方依赖**，升级时保留 |
| OCR | `server/ocr_server.py` | 独立进程，`127.0.0.1:8765`，rapidocr |
| MCP | `server/health_mcp.py` | stdio MCP agent，读写本机 API |

**结论：** 文档 §2 的「真实起点」基本准确；核心技术债是「全局状态耦合 + 整表替换 + 写入不等待结果」三项，升级必须逐项消解，否则换框架也无法解决并发覆盖和丢数据。

## 3. 前端升级方案（React + TypeScript + Vite）

### 3.1 工程结构（目标）
```
frontend/
  package.json          # react, react-dom, vite, typescript, @vitejs/plugin-react
  vite.config.ts        # dev server 代理 /api → FastAPI
  tsconfig.json
  index.html            # Vite 入口
  src/
    main.tsx            # ReactDOM.createRoot
    App.tsx             # 路由 + 布局壳
    api/
      client.ts         # 统一 fetch 封装（返回 Promise，await 到结果）
      types.ts          # 与 FastAPI OpenAPI 对齐的 TS 类型
    features/
      visits/           # 记就诊 → 查详情 → 编辑（样板闭环）
        VisitList.tsx
        VisitDetail.tsx
        VisitComposer.tsx
        useVisits.ts
    lib/
      echarts.ts        # 复用现有 ECharts 封装
      markdown.ts       # 复用 assets/markdown.js 逻辑
```

### 3.2 关键改造点（对齐文档 §2.1）

1. **消除全局状态**：用 React state / Context 替代 `let labs/state/reports` 等全局变量；数据以 hooks（`useVisits`）按域加载。
2. **写入必须 await 结果**：新 `api/client.ts` 的 `put()` 返回 `Promise<T>`，UI 组件 `await` 后再提示成功——直接修复 `app.core.js:855` 缺陷。验收：断网/HTTP 失败时不显示成功、输入保留。
3. **类型边界**：`api/types.ts` 手写（初期）或由 FastAPI OpenAPI 生成，`Visit`、`LabResult`、`Report` 等按文档 §4 记录模型定义。
4. **复用资产**：ECharts、markdown、parse 保留为 `lib/` 下模块，不重写、不引新依赖。

### 3.3 迁移策略（灰度，不中断旧页面）
- Vite 构建产物与旧 `index.html` **并存**；旧页面路径 `/index.html` 继续可用，新页面从 `/app/` 或独立端口进入。
- 每迁移一个功能（先「就诊」闭环），旧 JS 对应入口加只读跳转或保留。
- 全部核心流程迁完后，旧 `js/app.*.js` 归档到 `legacy/`。

## 4. 后端升级方案（FastAPI，复用现有逻辑）

### 4.1 分层（目标）
```
backend/
  app/
    main.py             # FastAPI app, CORS, 挂载 routers
    db.py               # SQLite 连接、WAL、迁移版本表
    models.py           # Pydantic 模型（对齐文档 §4）
    routers/
      visits.py         # 逐条 CRUD + expected_revision
      labs.py  reports.py  state.py ...
      ocr.py  ai.py  files.py
    services/
      features.py       # 复用 health_features.py 的 OCR/AI/chat 逻辑
  requirements.txt
```

### 4.2 与现有代码衔接
- **服务层复用**：`health_features.py` 的 `parse_image / chat / ai_models / refs / context` 等直接作为 service 调用，不重写。
- **路由替换**：现有 `do_GET/do_PUT/do_POST` 分支 → FastAPI `@router.get/post/put`。
- **过渡期并存**：`http.server`（`health_server.py`）在迁移期**只读兜底**，先切读接口给新前端，写接口双写完成后再下线路由；禁止新旧两套写路由同时对外（避免 §3.2 整表替换继续生效）。
- **MCP / OCR**：`health_mcp.py`、`ocr_server.py` 独立进程不受影响，通过 FastAPI 内部调用或保留端口。

### 4.3 存储层（保持 SQLite）必须补齐的三件事
1. **迁移版本表**：新增 `schema_version` 表，`init_db()` 的 `ALTER TABLE ... ADD COLUMN` 收敛为版本化迁移函数，替代零散幂等 ALTER。
2. **逐条写接口 + revision**：新增 `PUT /api/visits/{id}` 等**逐条**接口，请求带 `expected_revision`；服务端比较版本，不一致返回 `409 Conflict`，不覆盖。保留旧整表接口作兼容层，但标记 deprecated。
3. **事务与幂等**：增删改与审计在单事务完成；新增请求带幂等键（`Idempotency-Key` header），重复提交不产生副本。

> 存储仍是单机 `data/health.db`，本轮**不引入**多设备并发所需的变更日志/删除标记——那些留待文档 §6.3 的完整离线同步阶段。

## 5. 数据模型对齐（文档 §4 目标模型 → 首轮最小落地）

本轮先落地与「就诊闭环」相关的核心对象，字段尽量沿用现有表，避免大改：

| 目标对象 | 现有表 | 首轮动作 |
|---|---|---|
| 就诊 Encounter | `visit` | 复用，加 `revision INTEGER DEFAULT 0` |
| 报告 Report | `reports` | 复用，`file` 走受控读取（后续） |
| 用药 Medication Record | `medication` | 复用，不自动成为在用药 |
| 档案成员 Profile | `members`（文件名/图片目录） | 首轮保持本机切换 |
| 附件 Attachment | 原件目录 + `reports.file` | 首轮保持现状 |

## 6. 实施顺序与验收（对齐文档 P0→P2，去掉跨设备）

| 阶段 | 内容 | 验收证据 |
|---|---|---|

| D（收尾） | 旧 JS 归档、文档更新、把新流程接回主导航 | 旧页面只读可查，新页面可用 |

## 7. 风险与注意

- **双轨并存风险**：过渡期新旧写路由若同时生效，整表替换会覆盖逐条写入。**必须保证同一资源只有一条写入链**。
- **ECharts/markdown 资产**：保留为本地模块，不引 npm 版，避免离线能力退化。
- **OCR 不随 Web 前端在手机运行**：初期仍联网调用服务端 OCR（文档 §5.1）。
- **SQLite 单机边界**：只适用于「联网提交即入库」的单机/私有服务；一旦要跨设备多写，必须先完成 §4.3 的 revision + 逐条接口，否则会静默覆盖。
- **不宣称端到端加密**：服务端可读取数据供 OCR/AI 使用（文档 §7.1）。

## 8. 已落地脚手架（本次产出）

- `frontend/`：React + TS + Vite 工程骨架，含 `api/client.ts`（await 结果）、`api/types.ts`、就诊闭环三组件，可 `pnpm dev` 启动。
- `backend/`：FastAPI 骨架，复用 `server/health_features.py`，含 `db.py`（SQLite + schema_version）、`routers/visits.py`（逐条 CRUD + expected_revision）、`main.py`。
- 详细启动方式与后续待办见 §9。

> 脚手架以**独立目录新建**，不改动现有 `js/`、`server/health_server.py`、`index.html`，旧系统完全不受影响、可继续运行。

### 8.1 前端实测（已通过）
- `pnpm install` 成功（npm registry 可达）。
- `tsc --noEmit` 类型检查 **0 错误**（严格模式）。
- `pnpm build` 生产构建成功：`dist/index.html` + `dist/assets/index-*.js`（约 148 KB / gzip 48 KB）。

### 8.2 后端实测
- `python -m py_compile` 全部模块编译通过。
- `backend/smoke_test.py`（不依赖 FastAPI，纯 sqlite3）验证：迁移加 `revision` 列、旧记录 `revision=0`、`schema_version=1`、迁移幂等、逐条 create/update、**陈旧 revision 写入被拒**——全部通过；测试用临时库，**真实 `data/health.db` 未被触碰**。
- **HTTP 端到端（真启 uvicorn + 真 sqlite，临时库）**：`GET /api/health` / POST 建（revision=0）/ GET 列表 / GET 详情 / PUT 更新（→revision=1）/ PUT 陈旧（→409）/ DELETE 错版本（→409）/ DELETE 正确版本（→204）/ 删后 GET（→404）**全部符合预期**。
- 依赖安装：pip 走系统代理 `127.0.0.1:7900`（PyPI 可下载，但下载大量可选依赖时会卡）。**踩坑记录**：`uvicorn[standard]` 与 `fastapi>=0.110` 这类宽松版本会拉到 0.162/0.54 + opentelemetry 等重依赖并卡死；**已改为锁定稳定版** `fastapi==0.115.6 / uvicorn==0.32.1 / pydantic==2.10.3`，安装干净通过。
- 环境注意：SQLite 建 WAL 在 `%TEMP%`（沙箱外）会报 `unable to open database file`；测试须在工作区内目录（如 `backend/.testdb/`）或真实 `data/` 下进行。
